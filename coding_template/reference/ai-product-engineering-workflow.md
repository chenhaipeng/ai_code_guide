# AI 产品工程实战方法论

> 从一个 idea 到真正可用的产品，AI 编程需要的不只是 prompt，而是一套完整的工程约束体系。

## 核心洞察

2026 年的行业数据揭示了一个反直觉的事实：**有经验的开发者在 AI 辅助下实际速度变慢了 19%，但他们感觉自己快了 20%。** 代码重复率从 8.3% 升到 12.3%，安全问题高达人工代码的 2.74 倍，重构占比从 25% 降到不足 10%。

这些数字说明：AI 编程的瓶颈不是代码生成速度，而是**产品语义的清晰度、工程边界的明确度和验证标准的严格度**。

因此，正确的方法论是：

> 先用原型固定产品语义，用 AGENTS.md 固定 AI 行为，用系统设计固定数据链路，用 E2E 固定验收标准，最后让 AI 在这些约束内分阶段交付。

## 总体流程

```text
Idea 压缩
→ 产品规格
→ 原型定义（按需）
→ AI 行为宪法与工程 Harness (AGENTS.md / CLAUDE.md)
→ 系统设计
→ E2E 验收规范
→ 实施计划
→ 分阶段开发
→ 原型对齐（按需）
→ 验证交付
```

实际执行顺序以 `.template/AI-BOOTSTRAP.md` 的阶段表为准。本文件是方法论参考，不覆盖项目中的 `AGENTS.md` / `CLAUDE.md`、`docs/superpowers/specs/` 或 `.template/prompt.md`。

核心原则：**前重后轻**。上游投入越充分（原型、规格、约束），下游 AI 执行越精准、越少返工。

## 1. Idea 压缩

第一步不是写代码，不是画原型，而是把模糊想法压缩成一句话。

这句话必须回答五个问题：

- 目标用户是谁
- 用户在什么场景下使用
- 解决什么问题
- 带来什么结果
- **哪些事情第一版不做**（这个最容易忽略，也最重要）

示例：

```text
帮助世界杯球迷在赛前查看每场比赛胜平负预测、比分概率和晋级概率，并理解预测依据。
```

这句话决定了产品边界：它是预测分析工具，不是投注平台、新闻站、社区或完整体育数据平台。

**关键原则：边界由"不做什么"定义，而不是由"做什么"定义。**

如果一句话说不清，说明 idea 本身还没想透。不要进入下一步。

---

## 2. 原型定义

原型的目标是把一句话 idea 变成**可看、可点、可感受**的产品结构。此时不追求工程实现。

### 产出物

| 产出 | 说明 |
|------|------|
| 页面列表 | 产品包含哪些页面 |
| 用户路径 | 用户从进入到离开经过哪些步骤 |
| 信息架构 | 每个页面展示什么信息 |
| 关键组件 | 可复用的 UI 组件有哪些 |
| 竞品参考 | 对标哪些真实产品 |
| 视觉方向 | 配色、字体、整体调性 |
| MVP 范围 | 第一版包含哪些页面和功能 |
| **明确不做** | 哪些功能延后或放弃 |

### 关键做法

1. **让 AI 参考真实竞品设计原型**。给出 3-5 个对标产品名字，让 AI 提取它们的页面结构和交互模式。
2. **原型必须是可交互的**。静态截图不算原型。HTML 单文件是最好的形式——不需要构建工具，浏览器直接打开，所有页面、CSS、JS 都内联，方便 AI 后续对齐。
3. **原型一旦冻结，就变成后续实现的视觉和交互蓝图**。所有前端页面最终都要和原型视觉一致。

### 实战经验

我们的世界杯项目用了一个 5,724 行的 HTML 单文件原型，包含 7 个页面视图、完整 CSS 设计系统和内联 JS 交互。这个文件在后续开发中反复被用作：
- 前端实现的视觉对照标准
- CSS 变量和组件样式的提取来源
- 交互流程的验证基准

**如果原型不完整，后续开发会反复出现"和原型不一样"的问题，修复成本远大于原型阶段多花的时间。**

## 3. 产品规格

原型解决"长什么样"，产品规格解决"做什么"和"验收标准是什么"。

### 必须覆盖的内容

对每个页面，产品规格必须包含：

| 维度 | 示例 |
|------|------|
| 页面功能 | 比赛预测页展示胜平负概率、预测比分、近期战绩 |
| 用户故事 | 用户选择比赛 → 输入意图 → 选择深度 → 确认预测 → 查看报告 |
| 数据字段 | 每个展示元素对应后端哪个字段 |
| 数据来源 | 数据从哪来、如何采集、置信度如何 |
| 交互状态 | 正常、加载中、空状态、错误状态 |
| 空状态 | 无数据时页面显示什么（绝对不能白屏） |
| 错误状态 | 接口失败时页面如何降级 |
| 验收标准 | 具体可检查的条件 |

### 关键原则

**"数据不是前端写死的"必须作为验收标准写进规格，而不是事后口头约定。**

示例：

```text
比赛预测页：

- URL: /matches/{id}
- 数据来源: GET /api/predictions/{id}
- 胜平负概率必须来自 API，概率总和应约等于 100%
- 若预测数据缺失，显示"暂无预测"，不能白屏
- 若接口失败，显示"加载失败，请重试"，不能白屏
```

## 4. AI 行为宪法 (AGENTS.md)

AGENTS.md 不是代码规范，而是**AI 工程团队的行为宪法**。它定义 AI 在这个项目中能做什么、不能做什么、应该怎么做。

### 2026 年实证数据

Anthropic 研究发现：**AGENTS.md 中使用祈使句（"必须使用..."）的遵循率是 94%，而描述性语句（"本项目使用..."）只有 73%。**

社区最佳实践：**AGENTS.md 控制在 200-300 行以内。** 超过这个长度，AI 会开始忽略部分内容。一个精炼的 400 token 文件，效果优于 4,000 token 的冗长版本。

### 五个必须包含的部分

```text
1. 项目定位与边界 — 这是什么、不是什么、第一版不做什么
2. 技术栈与目录结构 — 精确到框架版本、目录名、文件命名规则
3. 构建/测试/启动命令 — 精确到可直接复制执行的字符串
4. 禁止事项 — 用"禁止"/"不允许"/"不得"等绝对语气
5. 验证标准 — 什么叫"做完"、什么叫"通过"
```

### 实战经验

我们的 AGENTS.md 有 348 行，包含 14 个章节。最有效的部分是：

- **禁止事项**（"禁止写死假数据冒充真实预测结果"、"禁止在 C 端文案中使用 token"）——这些硬约束直接阻止了 AI 最常见的跑偏行为
- **页面与接口规范**（22 行表格，精确到每个页面对应哪个 API 端点）——这让 AI 在实现时不会遗漏接口
- **数据链路规范**（从数据源导入到赛后评估的完整链路）——这确保 AI 不会跳过关键的数据追踪步骤

### 注意

AGENTS.md 应该在开发前写好，并在开发过程中持续更新。每次 AI 跑偏了，就把跑偏的行为写成新的禁止项。这是一种**纠偏驱动的迭代方式**。

## 5. 工程 Harness

Harness 是工程执行环境、约束和验证入口的集合。

### 必须明确的内容

| 项目 | 说明 |
|------|------|
| 技术栈 | 前端、后端、数据库、缓存、任务队列 |
| 项目结构 | 目录布局、文件组织规则 |
| 构建命令 | `npm run build`、`npx vite build` 等 |
| 启动命令 | 本地开发如何启动前后端 |
| 测试命令 | 单元测试、集成测试、E2E 测试如何运行 |
| 数据库初始化 | schema 如何创建、种子数据如何加载 |
| Mock 与真实数据边界 | 什么时候可以用 mock、什么时候必须用真实数据 |

### 选择技术栈的隐藏标准

不只看技术是否强大，还要看它**是否适合 AI 协作**：

- 文档是否充分（AI 需要查文档解决 API 调用问题）
- 错误信息是否清晰（AI 根据错误信息自我修正）
- 项目结构是否标准（AI 能预测文件应该放在哪里）
- 测试是否容易运行（AI 需要快速验证自己的修改）
- 构建是否稳定（构建失败会阻塞 AI 的迭代循环）

### 实战经验

我们的技术栈：Vue 3 + TypeScript + Vite / Python FastAPI + Pydantic / PostgreSQL + SQLAlchemy + Alembic / Redis。这套组合对 AI 协作非常友好：
- FastAPI 的错误信息精确到字段和行号
- Alembic 的迁移文件结构清晰
- Vite 的 HMR 让前端修改秒级可见
- Pydantic 的 schema 验证直接暴露数据问题

## 6. 系统设计

系统设计固定三个核心：**数据模型、数据链路、模块边界**。

### 数据链路设计

从数据来源到用户看到结果，每一步都要写清楚：

```text
数据源导入 → 标准化入库 → 预测前取快照 → Agent 读取快照
→ 生成报告 → 计费结算 → C 端报告页 / 管理台审计 → 赛后评估
```

### 数据模型设计

核心原则：

1. **每张表都要有明确的来源和用途**。不放"以后可能用到"的字段。
2. **不可变数据用快照**。预测用的数据必须在创建时锁定，后续数据更新不影响已生成的报告。
3. **每次余额变动都要写账本**。账本不可物理删除，这是审计的基础。

### 模块边界

MVP 阶段允许适度合并。我们的 FastAPI 后端用一个 2,355 行的单文件 `app.py` 包含 33 个路由端点。这个决策是有意为之——MVP 阶段单文件的可读性和可搜索性优于过早拆分的微服务结构。

**但必须在决策记录中写明"为什么这样做"和"什么时候拆分"。**

## 7. 实施计划

### 核心原则：不要让 AI 一次性实现整个系统

拆成可验证的 phase，每个 phase 包含：

| 要素 | 说明 |
|------|------|
| 目标 | 本 phase 要完成什么（一句话） |
| 输入 | 依赖哪些已完成的产出 |
| 输出 | 本 phase 完成后新增哪些文件/功能 |
| 修改范围 | 只允许修改哪些文件 |
| 验证命令 | 构建命令、测试命令、启动命令 |
| E2E 路径 | 本 phase 覆盖的用户路径 |
| 禁止事项 | 本 phase 不允许做的事 |

### 推荐拆分

```text
Phase 1: 项目初始化 + 页面骨架
Phase 2: 数据库表 + 种子数据
Phase 3: 核心后端 API
Phase 4: 预测/计算逻辑
Phase 5: 前端页面 + 真实 API 对接
Phase 6: E2E 验收
Phase 7: 部署 + 交付文档
```

### 实战经验

我们的项目产生了 4 个实施计划文档（1,050 + 482 + 153 + 570 行），前两个在实现前写好，后两个在实现过程中按需补充。最有价值的是最详细的那个 1,050 行的迁移计划——它把每个 API 端点拆成独立任务，每个任务有明确的输入、输出和验证标准。

**实施计划不是一次写完就固定的。它应该随着开发的推进不断更新。**

## 8. E2E 验收规范

**E2E 规范必须在开发前定义。** 原因：如果你在开发前没写清楚"怎么算通过"，你会在开发后不断降低标准。

### E2E 规范必须覆盖

| 维度 | 说明 |
|------|------|
| 访问路径 | 用户从哪个 URL 开始 |
| 操作步骤 | 用户点击什么、输入什么 |
| 关键接口 | 页面依赖哪些 API |
| 期望状态码 | 接口应返回什么 HTTP 状态 |
| 页面断言 | 页面上应该出现什么文字/元素 |
| 数据断言 | 返回的数据应该符合什么结构 |
| Console 检查 | 不应有 JavaScript 错误 |
| Network 检查 | 所有 API 请求应返回成功 |
| 失败状态 | 接口失败时页面应如何降级 |

### 2026 年的验证最佳实践

Anthropic 工程团队的验证方法：

> "给 AI 一个可以运行的检查：测试、构建命令、截图对比。这是'你盯着看的 session'和'你可以走开的 session'的区别。"

验证层次：

1. **单文件检查**：lsp_diagnostics、类型检查
2. **构建验证**：`npm run build` / `pytest` 通过
3. **API 验证**：curl 调用真实后端，检查返回数据
4. **浏览器验证**：Chrome DevTools 检查页面渲染、Network 请求、Console 错误
5. **完整用户路径**：从注册到完成预测到查看报告的完整链路

### 实战经验

我们的项目在 AGENTS.md 中定义了完整的 Chrome DevTools E2E 验证链路：

```text
注册 → 登录 → bootstrap → 钱包 → 赛程/价格 → 意图解析
→ 费用预估 → 创建预测 → SSE 进度 → 报告 → 账本
→ 历史 → 管理台详情 → 数据链路 → 数据快照 → 录入赛果 → 预测评估
```

每一步都必须记录真实证据：user_id、balance、prediction_id、data_snapshot_id、ledger entries 等。**"应该可以"不算验证。**

## 9. 分阶段开发

### 开发循环

```text
读取上下文（AGENTS.md + 进度文件）
→ 明确本 phase 范围
→ 实现最小改动
→ 运行构建
→ 运行测试
→ 执行 E2E
→ 修复问题
→ 记录验证报告
```

### Prompt 工程的实证规律

2026 年的学术研究发现，以下 prompt 策略有实证效果：

| 策略 | 效果 | 适用场景 |
|------|------|----------|
| 明确输入输出格式 | 44% 的改进 prompt 包含此项 | 所有场景 |
| 提供算法细节和公式 | 57% 的改进 prompt 包含此项 | 复杂逻辑 |
| 用"必须"而非"应该" | 提升遵循率 | 约束类指令 |
| 一条硬规则胜过二十条建议 | +22% 准确率 | 系统指令 |
| 实现和测试分开生成 | +15% 实现准确率 | 代码生成 |
| 单函数不用 chain-of-thought | 0% 或负效果 | 简单任务 |
| 跨文件任务用 chain-of-thought | +26% 准确率 | 多文件修改 |

### AI 代码的已知失败模式

以下问题在 AI 生成的代码中反复出现，必须在代码审查时重点检查：

| 失败模式 | 说明 |
|----------|------|
| 幻觉验证 | TypeScript 类型写了但无运行时检查 |
| 遗漏鉴权 | 新增路由忘记加 auth middleware |
| 越权访问 | 认证了用户但信任 URL 中的 ID |
| 竞态条件 | 先检查再操作的逻辑在并发下出错 |
| 资源泄漏 | 错误路径上不释放连接/资源 |
| 重试风暴 | 无退避、无抖动、无幂等 |
| 上帝组件 | 单个 prompt 生成 400+ 行函数 |
| 孤立迁移 | 改了 schema 但没写 migration |
| console.log 可观测性 | 无结构化日志、无错误追踪 |
| 静默失败 | 代码不报错但结果不对（最危险） |

### 关键做法

1. **一次只让 AI 做一件事**。不要"帮我实现整个模块"。而是"请只实现 Phase 3 中的用户注册接口"。
2. **做完立刻验证**。不要攒 10 个改动再一起验证。
3. **记录决策**。每次遇到需要选择的地方，记录选择了什么、为什么、备选方案是什么。这不仅是文档，更是后续 AI session 的上下文。

## 10. 验证交付

可交付产品不是"代码写完"，而是**能被访问、能被演示、能被验证、能被维护**。

### 交付检查清单

```text
□ 可以访问部署地址（本地或线上）
□ 核心页面可用且不是空白
□ 数据来自真实 API，不是前端写死
□ 空状态和错误状态有降级展示
□ 构建通过（零 error）
□ 测试通过（零 failure）
□ E2E 用户路径完整走通
□ Console 无 JavaScript 错误
□ Network 请求全部返回成功
□ 有已知问题列表
□ 有下一步计划
```

### 交付报告模板

```text
1. 产品访问地址
2. 本次完成范围
3. 构建结果
4. 测试结果
5. E2E 验证路径和证据
6. 关键接口验证结果（含真实返回数据）
7. 数据库验证结果
8. Console / Network 检查结果
9. 未验证项和原因
10. 已知问题
11. 决策记录
12. 下一步建议
```

## 什么会失败

基于 Columbia 大学的研究和社区实践，以下是最常见的失败模式：

### 1. 直接让 AI 从 idea 开始写代码

跳过原型和规格，直接"帮我做一个世界杯预测网站"。结果：AI 生成一个和你的想法完全不同的东西，你花更多时间纠偏。

### 2. 没有冻结原型就开始开发

原型没定稿就写前端。开发过程中原型和实现之间不断产生差异，最终两边都对不上。

### 3. AGENTS.md 太长或太模糊

超过 300 行的 AGENTS.md 会被 AI 忽略后半部分。模糊的指令（"尽量使用好的设计"）没有任何约束力。

### 4. 没有禁止事项

AI 最常见的跑偏方式是**过度实现**：你让它加一个按钮，它加了一个按钮 + 动画 + 三种状态 + 国际化。禁止事项就是提前告诉 AI "不要做这些"。

### 5. 不验证就继续

AI 说"已完成"，你直接进入下一个任务。三天后发现之前的实现有 bug，但已经在新代码上叠加了更多依赖。修复成本指数级增长。

### 6. Mock 数据不清理

开发初期用 mock 数据是合理的，但如果不在 AGENTS.md 中明确"什么时候必须切换到真实数据"，mock 会一直留到上线。

## 检查清单：按阶段

### 开发前

- [ ] 一句话 idea 已写清（含"不做什么"）
- [ ] 原型已完成并可交互
- [ ] 产品规格已覆盖所有页面（含空状态和错误状态）

## 总结

这套方法论的核心不是让 AI 写出更多代码，而是**建立一个 AI 能稳定协作、持续迭代、真实交付的工程系统**。

最终目标是：你给出一个 idea，经过这套流程，产出一个**你能访问、能演示、能验证、能维护**的产品。而不是一个"看起来有代码但跑不起来"的项目。

```text
产品语义的清晰度，决定了 AI 输出的精准度。
工程边界的严格度，决定了 AI 执行的可靠度。
验证标准的明确度，决定了最终交付的可信度。
```
