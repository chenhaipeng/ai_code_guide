## E2E 前置环境检查

E2E 执行前必须确认：

- [ ] 数据库 / 核心存储服务运行正常。
- [ ] 缓存 / 队列 / 中间件运行正常（如适用）。
- [ ] 后端服务真实启动，启动日志无致命异常。
- [ ] 前端 dev server 或生产构建产物可访问。
- [ ] 测试账号可登录，角色和权限范围明确。
- [ ] 如依赖外部服务或测试数据，必须记录其状态。

如果任一前置条件不满足，不能宣称 E2E 通过，必须在 verify 报告中记录阻塞原因。

## 缺陷分级

| 等级 | 判定标准 | 是否允许通过 |
| --- | --- | --- |
| Blocker | 系统无法启动、核心路径不可访问、数据丢失 | 否 |
| Critical | 核心接口 500、权限绕过、敏感信息泄露、审计链断裂 | 否 |
| Major | 核心功能不可用、关键展示错误、主要交互失败 | 否 |
| Minor | 文案、样式、非核心字段问题 | 可登记后通过 |

最终通过必须满足：无 Blocker、Critical、未解决 Major 缺陷。

## 验收报告格式

验收报告必须写入固定目录：

```text
docs/e2e/verify/
```

命名规则：

- 单个 spec / 单个路径验收：`<spec-name>-verify.md`
- 总体验收：`<topic>-overall-verify.md`

复杂项目必须一份 spec 对应一份 verify 报告；总体验收另写 overall verify 报告。

每份 verify 报告至少包含：

- 验收日期
- 代码分支 / commit（如适用）
- 对应 spec 或验收路径
- 环境状态（中间件、后端、前端、账号）
- 构建结果（后端编译、前端构建）
- 总用例数 / 通过数 / 失败数
- 失败项详情
- 页面 / 功能结果（布局、交互、截图）
- 关键 API 状态码和返回摘要
- 关键数据 ID 或数据库查询结果
- Console / Network 汇总（JS error、401/403/404/500、接口路径错误）
- 截图路径清单
- 缺陷列表（按分级）
- 未验证项与原因
- 最终结论：通过 / 有条件通过 / 不通过
